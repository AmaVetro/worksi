ESTANDARES GENERALES API
- Base URL: /api/v1
- Formato: application/json salvo endpoints multipart.
- Charset: UTF-8.
- Fechas en respuestas: ISO-8601 UTC (ejemplo: 2026-04-25T03:10:00Z).
- Ids: enteros sin signo (BIGINT en BD), expuestos como number JSON.
- Moneda/sueldo: enteros (CLP) sin decimales.
- Convencion de nombres:
  - JSON de API publica: snake_case (ejemplo: first_name, region_id).
  - Codigo Java interno (entidades/DTOs/servicios): camelCase.
  - Mapeo JSON snake_case <-> Java camelCase: obligatorio mediante configuracion de serializacion o anotaciones explicitas en DTOs.
- Paginacion estandar:
  - Query params: page (base 1), size (default 20, max 100), sort (campo,asc|desc).
  - Respuesta: items, page, size, total_items, total_pages.


AUTENTICACION Y SESION
- JWT solo access token (sin refresh).
- Header en rutas protegidas:
  Authorization: Bearer <token>
- Familias de credencial:
  - Publicas: sin Authorization.
  - Autenticadas: Bearer <access_token> emitido por POST /api/v1/auth/register/candidate, POST /api/v1/auth/login u operaciones de alta por administrador que creen usuarios ADMIN o RECRUITER. Claim de rol en token: CANDIDATE, ADMIN o RECRUITER.
- Login unico web: POST /api/v1/auth/login. Segun rol en respuesta, el frontend redirige a portal administrador (ADMIN) o a sesion empresa (RECRUITER). Misma pantalla de login para ambos.
- Roles en JWT de aplicacion:
  - CANDIDATE
  - ADMIN (portal de administracion y rutas /api/v1/admin/*)
  - RECRUITER (vinculado a companies.id; todas las rutas /api/v1/company/*)
- Contrasenas en persistencia solo en users.password_hash (bcrypt u algoritmo acordado) para usuarios que inician sesion CANDIDATE, ADMIN y RECRUITER. La empresa en companies no tiene credencial ni campo de contraseña en datos.
- Cuenta ADMIN inicial en entorno de desarrollo o prueba puede sembrarse en migracion Flyway con INSERT en users que solo establece password_hash (por ejemplo bcrypt), sin publicar texto plano en el repositorio. Este contrato no incluye ninguna contrasena literal para ADMIN; la cadena que valida ese hash debe acordarse fuera de este archivo u operativa del equipo.
- Politica de contraseña (registro candidato, alta reclutador por ADMIN, y paso definitivo de recuperacion donde se envia nueva contraseña — ver «Recuperacion de contraseña — regla de producto»): el texto claro debe cumplir como minimo: longitud minima 10 caracteres; al menos una letra mayuscula; al menos una letra minuscula; al menos un simbolo; al menos un digito numerico. El backend rechaza con error de validacion si no se cumple; en persistencia solo password_hash.
- Logout: elimina sesion en cliente (backend no mantiene blacklist de tokens).

ENUMS OFICIALES
- role: CANDIDATE | ADMIN | RECRUITER
- modality: REMOTE | HYBRID | ONSITE
- workload: FULL_TIME | PART_TIME | OTHER
- job_status: ACTIVE | INACTIVE | DELETED
- application_status: APPLIED | VIEWED | CANCELLED
- swipe_action: PASS | APPLY



CONSTRUCCION OBLIGATORIA DE job_text (BACKEND)
- job_text se construye concatenando solo:
  - title
  - description
  - modality
  - workload
- No existe campo separado requirements en persistencia de oferta; todo texto libre del puesto va en description (Flujo Pantallas App Web).
- No incluir en job_text concatenado:
  - job_skills
  - salary_offered
  - years_experience_required (entra al score como dimensión estructurada experience_score; ver CONTRATO DE SCORE FINAL)
  - company_commercial_name (solo referencia de marca en listados; no forma parte del texto semantico de matching salvo decision explicita futura de producto)



FAIRNESS OBLIGATORIO (ANTES DE EMBEDDINGS)
- Orden: regex inicial -> spaCy NER -> regex final.
- spaCy: PERSON, ORG, GPE.
- Regex: edad, genero, nacionalidad, institucion procedencia, email, RUT y menciones de años de experiencia declarados dentro del CV.
- Solapamiento selectivo obligatorio en: nombre, institucion, nacionalidad.
- No eliminar ORG de forma indiscriminada.

ENDPOINTS DE AUTENTICACION

1) Registro candidato
- POST /api/v1/auth/register/candidate
- Auth: publica
- Momento funcional: unico request de alta, despues de que el postulante avanza por "Crear cuenta" -> (CV, skills, preferencias) en UI -> pantalla "Uso de datos" acepta consentimiento. Ahi el cliente envia de una vez identidad, password, preferencias, skills, rubro, CV y consent_given=true. No existen filas "borrador" en backend: todo se persiste en la misma operacion o falla.
- Content-Type: multipart/form-data; charset=UTF-8
- Partes (multipart, nombres oficiales):
  - "data" (string JSON, application/json en la parte): cuerpo logico con todos los campos de registro y perfil inicial (ver abajo). obligatorio.
  - "file" (binario, filename *.pdf, application/pdf): PDF del CV. obligatorio al menos en el flujo movil con pantallas que exigen subir CV antes de "Uso de datos" (mismo limite: max 1MB, solo PDF). Si se acordase flujo alterno sin CV, debe documentarse en OpenAPI; por defecto el contrato de producto exige el archivo.
- Cuerpo logico (JSON en la parte "data"):
{
  "email": "correo@dominio.cl",
  "password": "Aa!1234567890",
  "first_name": "Juan",
  "middle_name": "Eduardo",
  "last_name_paternal": "Ramirez",
  "last_name_maternal": "Perez",
  "phone": "+56912345678",
  "rut": "12345678-5",
  "document_number": "12345678",
  "street": "Av. Siempre Viva 123",
  "region_id": 7,
  "commune_id": 77,
  "consent_given": true,
  "sector_id": 1,
  "profile_summary": null,
  "salary_expected_min": 700000,
  "salary_expected_max": 1200000,
  "preferred_modalities": ["REMOTE", "HYBRID"],
  "preferred_workloads": ["FULL_TIME", "OTHER"],
  "skills_ids": [10, 11, 12]
}
- Validaciones (data + file):
  - email formato valido y unico.
  - password segun politica obligatoria (minimo 10 caracteres; al menos una mayuscula, una minuscula, un numero y un simbolo).
  - RUT valido (digito verificador).
  - comuna debe pertenecer a region.
  - consent_given debe ser true.
  - la pantalla "Uso de datos" es la ultima pantalla antes de persistir en backend: consent_given y alta ocurren juntos.
  - skills_ids entre 3 y 12; sector_id requerido segun reglas de producto; preferred_modalities y preferred_workloads coherentes con enums; rango sueldo coherente si ambos informados.
  - file: solo PDF, max 1MB, tipo application/pdf; debe coincidir con reglas de storage del backend.
- Response 201:
{
  "user_id": 101,
  "role": "CANDIDATE",
  "access_token": "jwt",
  "token_type": "Bearer",
  "expires_in": 3600
}
- Nota: el cliente mantiene en estado local (memoria de app) los datos y el archivo de CV mientras recorre las pantallas anteriores a "Uso de datos"; el backend no persiste nada de candidato hasta este POST. Si se pierde el estado (cierre forzado de app), el usuario reingresa la informacion.



2.1) Alta empresa (administrador del sistema)
- POST /api/v1/admin/companies
- Auth: Bearer ADMIN
- Content-Type: multipart/form-data; charset=UTF-8
- Partes (nombres oficiales):
  - "data" (string JSON, application/json en la parte): obligatorio, perfil empresa (corporate_email obligatorio de contacto corporativo; sin contrasena ni cuenta de login para la empresa; la empresa no es cuenta de usuario).

- Cuerpo logico JSON en parte "data":
{
  "commercial_name": "Empresa X",
  "legal_name": "Empresa X SPA",
  "phone": "+56912345678",
  "corporate_email": "contacto@empresax.cl",
  "address": "Av. Ejemplo 123, Oficina 4",
  "rut": "76123456-7",
  "region_id": 7,
  "commune_id": 77,
  "sector_id": 1,
  "worker_count_approx": 50
}
- Validaciones: RUT valido y formato UI, comuna-region consistente, commercial_name legal_name phone corporate_email address obligatorios; corporate_email formato email valido (max 254); image opcional.
- Response 201:
{
  "company_id": 201
}

Recuperacion de contraseña — regla de producto (movil CANDIDATE y web ADMIN/RECRUITER)
- El bloqueo tras 4 intentos fallidos consecutivos de login es real (misma regla Contrato para login) y debe mostrar las pantallas de recuperacion como derivacion UX.
- No existe recuperacion efectiva basada en codigo enviado o generado para el usuario: nunca se entrega ni se exige validar contra backend un OTP/codigo real como condicion para cambiar contraseña.
- Las pantallas y botones de «solicitar codigo», «ingresar codigo» y «reenviar codigo» son solo maqueta: no cumplen funcion de recuperacion real ni obligan al usuario a un codigo valido; el cliente debe permitir continuar con cualquier texto escrito en el campo de codigo.
- La unica parte obligatoria y real del flujo es la pantalla de nueva contraseña: al confirmar ahi con politica valida, el cambio debe persistir de inmediato en backend (`users.password_hash`) y el usuario debe poder iniciar sesion con la nueva clave.
- La pantalla de «confirmacion en bandeja» (o mensaje equivalente) no implica envio de correo ni enlace real.
- Los endpoints siguientes son referencia tecnica; el cierre con persistencia ocurre en el paso de nueva contraseña. Como el cliente no depende de un codigo real, backend y clientes deben alinearse para que ese cierre sea posible sin flujo OTP (p. ej. mecanismo interno con `recovery_token`).

CHAT Y MATCH (MENSAJERIA RECLUTADOR <-> CANDIDATO)

Pendiente de implementacion en backend. Las secciones 28-33 definen el contrato de los endpoints /api/v1/chat/*.

Reglas generales:
- Una conversacion vincula exactamente a un reclutador (quien la inicia) y un candidato.
- Solo esos dos usuarios pueden listar mensajes y enviar mensajes en esa conversacion; otros reclutadores u otros candidatos reciben 403.
- El reclutador inicia el match desde flujo web (perfil candidato / postulacion); el candidato no puede crear conversaciones.
- En cliente movil el candidato ve company_commercial_name de la empresa del reclutador, no el nombre personal del reclutador.
- Primer mensaje al establecer match: maximo 80 caracteres (campo first_message en POST conversacion).
- Mensajes posteriores: maximo 500 caracteres por mensaje (campo body en POST mensaje).
- Sin WebSockets: clientes refrescan con polling usando GET mensajes y query param after_message_id.
- No hay adjuntos ni notificaciones push.

MATCHING API EXTERNA (CONSUMIDA SOLO POR SPRING)

34) Match interno IA (ai-service)
- GET /health — ver seccion 0.1
- POST /match (FastAPI)
- URL interna: http://ai:8000/match en Docker Compose; Spring Boot usa WORKSI_AI_BASE_URL
- Request:
{
  "cv_text": "texto cv limpio",
  "job_text": "texto oferta permitido"
}
- Response:
{
  "score": 0.8215,
  "explanation": "Coincidencia en experiencia backend y herramientas"
}
- Reglas:
  - score de FastAPI es aporte semántico cuando aplique llamada /match.
  - Spring calcula las cinco dimensiones y final_score según CONTRATO DE SCORE FINAL.



CONTRATO DE SCORE FINAL (BACKEND -> FRONT)
- El porcentaje final (0..100, dos decimales) combina cinco dimensiones con peso igual (20% cada una):
  final_score = clamp( (description_score + title_score + modality_score + workload_score + experience_score) / 5 , 0, 100 )
- Dimensiones (cada una score 0..100):
  - description_score: similitud semántica cv_text (post-fairness) vs description de la oferta.
  - title_score: similitud semántica cv_text vs title de la oferta.
  - modality_score: 100 si modality de la oferta está en preferred_modalities del candidato; 0 si no coincide.
  - workload_score: 100 si workload de la oferta está en preferred_workloads del candidato; 0 si no coincide.
  - experience_score: comparación years_experience_required de la oferta vs years_experience del perfil del candidato (declarado en registro/edición de perfil); si no hubiera valor, 0.
- POST /match (FastAPI) puede aportar similitud semántica base; Spring calcula dimensiones y final_score.
- Objeto match_breakdown (obligatorio cuando la respuesta incluya match para candidato o listado/detalle postulaciones empresa):
{
  "final_score": 82.15,
  "description_score": 78.50,
  "title_score": 85.00,
  "modality_score": 100.00,
  "workload_score": 100.00,
  "experience_score": 75.00
}
- En respuestas con match al candidato: incluir match.score (= final_score), match.explanation_short o match.explanation, y match.match_breakdown.
- En GET /api/v1/company/jobs/{job_id}/applications: incluir match_score y match_breakdown por fila segun ejemplo seccion 26.
- Redondeo de respuesta: dos decimales (DECIMAL 5,2).




CODIGOS HTTP POR TIPO DE RESULTADO
- 200: consulta/actualizacion exitosa.
- 201: recurso creado.
- 400: request invalido.
- 401: sin token o token invalido.
- 403: sin permisos sobre recurso.
- 404: recurso no encontrado.
- 409: conflicto (ejemplo: email duplicado, postulacion duplicada).
- 413: archivo excede tamano permitido.
- 415: tipo de archivo no soportado.
- 422: regla de negocio incumplida.
- 429: limite de intentos/rate limit.
- 503: IA no disponible.
