
📘 WorkSí — Documento Oficial del Proyecto (Versión Final Consolidada)
1. INTRODUCCIÓN

WorkSí es una plataforma de reclutamiento laboral que combina una aplicación móvil para candidatos (rol CANDIDATE) y una aplicación web para administración del sistema (rol ADMIN) y operación de ofertas por reclutadores vinculados a una ficha empresa (rol RECRUITER), integrando inteligencia artificial para mejorar el proceso de selección mediante un sistema de matching semántico. El detalle de endpoints y campos oficiales está en Flujo Pantallas App Web y Contrato Unificado API.

El sistema permite a los candidatos interactuar con ofertas laborales mediante una experiencia tipo swipe, mientras que en la web el administrador da de alta empresas (sin usuario de login para la empresa) y reclutadores; quienes publican ofertas y revisan postulantes lo hacen autenticados como RECRUITER según ese mismo contrato.

El objetivo principal es optimizar el proceso de selección, reducir sesgos y mejorar la calidad del matching entre candidatos y empleos.

2. PROBLEMA A RESOLVER

Los sistemas actuales de reclutamiento presentan múltiples deficiencias:

Postulaciones masivas sin filtrado real
Matching basado en palabras clave poco preciso
Alto costo de revisión manual
Falta de transparencia en los procesos
Presencia de sesgos (edad, género, nacionalidad, etc.)
Experiencias de usuario poco modernas
3. PROPUESTA DE VALOR

WorkSí propone:

Matching inteligente basado en IA
Explicación simple del resultado del match
Interfaz moderna tipo swipe
Reducción de sesgos mediante procesamiento previo de datos
Experiencia diferenciada para candidatos (móvil) y para administración/reclutamiento (web)

10. SISTEMA DE FAIRNESS (CRÍTICO)

El sistema implementa un doble filtro de eliminación de datos sensibles:

10.1 Uso de spaCy (NER)

Detección de entidades:

PERSON
ORG
GPE
en este contexto, ORG también cubre institución de procedencia (universidad, instituto, centro de formación)
en texto libre donde regex no llega bien
Responsabilidad principal de spaCy: detectar nombre (PERSON), instituciones en redacción libre (ORG) y menciones geográficas/países en contexto no estructurado (GPE) para reforzar detección de nacionalidad indirecta.
Nota de implementación: no eliminar todo ORG de forma indiscriminada; priorizar remoción de institución de procedencia para no borrar contexto profesional útil del CV.
10.2 Uso de Regex

Detección de:

Edad
Género
Nacionalidad
Institución de procedencia (cuando aparezca en formatos detectables)
Email
RUT
Años de experiencia declarados dentro del CV
en campos con formato claro
Responsabilidad principal de regex: capturar patrones explícitos y estructurados (email, RUT, edad en formato directo, género etiquetado, nacionalidad declarada, años de experiencia declarados dentro del CV y bloques formateados de educación/institución).
Estrategia de doble filtro: regex + spaCy con solapamiento selectivo en nombre, institución de procedencia y nacionalidad para maximizar cobertura sin sobreeliminar información profesional relevante.
Orden recomendado del pipeline de fairness: primer barrido regex, luego spaCy sobre texto libre y cierre con un barrido regex final para escapes de formato.
Objetivo del filtro:

Eliminar atributos sensibles antes del procesamiento para:

Reducir sesgos en el matching
Evitar discriminación

Atributos sensibles objetivo del filtro:

Nombre
Edad
Género
Nacionalidad
Institución de procedencia
Correo
RUT
Años de experiencia declarados dentro del CV (si aparecen en el texto del CV)

⚠️ Importante:

El sistema reduce sesgos, pero no los elimina completamente.

11. MATCHING
Input (ilustrativo; cv_text proviene del texto extraído con Tika y la limpieza previa; job_text resume title+description+modality+workload para similitud semántica. El score final del producto combina cinco dimensiones — description, title, modality, workload y años de experiencia — según Contrato Unificado API):
{
  "cv_text": "...",
  "job_text": "..."
}
Output:
{
  "score": 0.82,
  "explanation": "Coincidencia en habilidades: Java, Spring Boot"
}
Explicación del match (simplificada)

Se basa en:

Coincidencias entre el texto del CV (tras fairness) y fragmentos de la oferta (description, title)
Modalidad de la oferta vs modalidades preferidas del postulante
Carga horaria de la oferta vs cargas horarias preferidas del postulante
Años de experiencia requeridos por la oferta vs years_experience del perfil del candidato (declarado en registro/edición; la redacción literal de años en el CV se retira del cv_text por fairness y no sustituye al valor de perfil; experience_score y match_breakdown HU-28 según Contrato)

❗ No se implementan explicaciones complejas

No se utilizan para el porcentaje de matching en la app móvil de postulantes:

Skills del perfil del postulante
Presentación personal escrita en perfil (fuera del CV)
Rango de sueldo esperado declarado por el postulante
Sueldo ofrecido en la oferta
Nacionalidad del postulante

12. BACKEND (API REST)
Convención de nombres backend/API:
JSON expuesto por API: snake_case.
Código Java interno (entidades/DTOs/servicios): camelCase.
El puente entre ambos se implementa con mapeo explícito (anotaciones/configuración de serialización) para mantener contrato estable.

12.1 Autenticación
Registro candidato en app móvil vía POST /api/v1/auth/register/candidate (multipart) tras consentimiento; en web MVP no hay registro público de empresa: alta empresa y reclutadores solo por ADMIN (Contrato Unificado API).
Login unificado web (ADMIN y RECRUITER) y login candidato (móvil): POST /api/v1/auth/login; JWT solo access token; roles oficiales CANDIDATE, ADMIN, RECRUITER (sin usuario empresa ni rol COMPANY).
En app móvil de postulantes y en web (admin/reclutador): bloqueo tras 4 intentos fallidos de login y derivación a pantallas de recuperación (regla Contrato MVP v1.15).
En MVP la recuperación no usa código OTP real para el usuario: pantallas intermedias maqueta; solo la nueva contraseña persiste en backend; sin mensajes reales al correo.
12.2 Módulo Candidatos
CRUD perfil
Subida de CV (PDF en filesystem; referencia en BD; extracción con Tika; MVP: solo PDF con texto seleccionable, sin OCR)
Gestión de skills en perfil (persistidas; no intervienen en el porcentaje ni en el request de matching)
Consentimiento obligatorio para uso de datos en pantalla "Uso de datos", que es la última pantalla antes de crear la cuenta del postulante; al aceptar el consentimiento se crea la cuenta y se pasa a Perfil
En app móvil de postulantes: carga de CV con límite de 1 MB
En app móvil de postulantes: selección de skills con mínimo 3 y máximo 12 en el flujo de registro (pantallas previas a "Uso de datos", estado en cliente) o en edición de perfil autenticado
12.3 Módulo Ofertas
Crear (HU-15; closing_date obligatorio; status inicial ACTIVE)
Editar oferta reclutador HU-16 (Sprint 8; PATCH /api/v1/company/jobs/{job_id}; incluye closing_date)
Ciclo de vida oferta HU-17 (Sprint 9; plan obligatorio MVP): activar/desactivar PATCH /api/v1/company/jobs/{job_id}/status (ACTIVE|INACTIVE); eliminar DELETE soft delete → DELETED
Estados job_status: ACTIVE | INACTIVE | DELETED; filtro listado CLOSING_DUE (guía visual por closing_date; sin cierre automático — HU-18 excluido)
12.4 Módulo Postulaciones
Crear postulación
Listar postulaciones
Desglose score matching reclutador HU-28 (GET /api/v1/company/jobs/{job_id}/applications con match_score y match_breakdown)
Cancelar postulación (solo si sobra tiempo)
Marcar postulación como VIEWED de forma automática en servidor cuando el reclutador publicador abre el detalle de una postulación concreta (HU-23; pantallas «Ver postulación» o «Perfil postulantes»); idempotente; no al listar postulantes ni al postular el candidato; no requiere botón manual en UI.

15. TESTING

No se implementa testing en los frontends: no se añaden carpetas de testing ni frameworks de prueba de UI en la web (React) ni en la app móvil. Los integrantes de frontend se limitan a comprobar visualmente y por uso que las pantallas y flujos respondan como se espera.

Sprint 12: tests automatizados de integración solo sobre funcionalidades más críticas — pipeline IA (extracción Tika, fairness, POST /match), seguridad auth (política contraseña, JWT, bloqueo tras 4 intentos), postulación, chat mínimo e integración Spring Boot ↔ FastAPI. Pipeline GitHub Actions ejecuta esa suite y falla el build si regresa Tika, IA o integración esencial.

Sprint 13: pasada E2E manual candidato + flujo empresa (reclutador, incl. match/chat), corrección de bugs críticos, demo stakeholder; comprobación puntual con Postman sobre endpoints prioritarios si aplica.

❌ No se realizan: tests de performance avanzados, suites E2E automatizadas en frontends, ni cobertura de funcionalidades no críticas o sencillas.
