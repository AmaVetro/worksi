Flujo de las pantallas de app móvil WorkSí

Este documento describe el flujo de pantallas de la app móvil para postulantes (rol CANDIDATE). Login del sitio web para administrador (ADMIN) y reclutador (RECRUITER), catálogo de endpoints oficiales y modelo de datos en MySQL quedan definidos en Flujo Pantallas App Web.txt, Contrato Unificado API - WorkSí.txt y en las migraciones Flyway bajo producto/backend/src/main/resources/db/migration/.

No es que realmente se utilice una pantalla para cada cosa: aquí se divide en pantallas distintas por fines explicativos. En la app móvil será la misma pantalla o componente en algunos casos, con textos o botones que van apareciendo u ocultándose según el paso.

Implementación de referencia: producto/frontmovil (Kotlin + Jetpack Compose). Rutas en AppNavigation.kt.



1. App Móvil (postulantes):

Pantalla breve inicial (splash):
- Ruta: splash.
- Pantalla corta de marca o transición; luego deriva a welcome. No cambia reglas de negocio ni endpoints.

Pantalla "al abrir la app" (bienvenida):
- Ruta: welcome.
- Botones "Iniciar sesión" → login y "Crear cuenta" → register_personal.
- El splash siempre lleva a welcome; no hay auto-login con token guardado (aunque SecureTokenStore persista el JWT tras login o registro).



Pantalla Iniciar Sesión:
- Ruta: login.
- Email y contraseña; botón "iniciar sesión" → POST /api/v1/auth/login.
- Botón "Olvidé mi contraseña" → recovery_email.
- Validaciones de email y contraseña en UI y backend.
- Bloqueo tras 4 intentos incorrectos (misma regla que web): respuesta de negocio en login → pantalla recovery_locked.
- Tras login exitoso → session (pantalla principal de ofertas / HomeScreen).
- Pendiente: aviso post-login a pantalla completa (GET /api/v1/messaging/conversations/login-notice) cuando exista mensajeria en backend y movil; una sola vez por conversacion (ver o cerrar aviso → PATCH dismiss-login-notice).



Pantalla "Recuperar contraseña" (bloqueo):
- Ruta: recovery_locked.
- Mensaje "Excediste el límite de intentos. Por nuestros lineamientos de seguridad, deberás recuperar tu contraseña", botón "Recuperar contraseña" → recovery_email.



Pantalla "Olvidé mi contraseña":
- Ruta: recovery_email.
- Campo email; botón "Enviar código". No hay recuperación real por este paso: es maqueta para continuar el flujo. Avanza a recovery_code sin código verdadero. Opcionalmente POST /api/v1/auth/password-recovery/request.



Pantalla "Ingresa tu código":
- Ruta: recovery_code.
- Campo código y botón "Ingresar código"; "Enviar nuevo código". El usuario puede escribir cualquier valor y avanzar a recovery_new_password. Opcionalmente POST /api/v1/auth/password-recovery/verify y request (reenviar).



Pantalla "Nueva contraseña":
- Ruta: recovery_new_password.
- Campo nueva clave y textos de política (mínimo 10 caracteres; mayúscula, minúscula, número y símbolo).
- Botón "Aceptar" → POST /api/v1/auth/password-recovery/reset; éxito → recovery_success.



Pantalla "Confirmar en bandeja":
- Ruta: recovery_success.
- Mensaje simulado sobre correo; contraseña ya aplicada. Botón "Volver a Log In" → login.



Pantalla "Crear cuenta":
- Ruta: register_personal.
- Campos obligatorios: nombre, apellido paterno, apellido materno, correo, contraseña (política del Contrato), celular, rut (validación chilena), nro. documento, región y comuna (GET /api/v1/catalogs/regions y .../communes).
- Opcionales: segundo nombre, calle.
- No se registra consentimiento aquí; ocurre en register_consent.
- Si falta un obligatorio: mensaje "Completa este campo".
- Avanza a register_cv sin persistir candidato en backend.



Pantalla "Subir CV":
- Ruta: register_cv.
- Una sola vista para elegir PDF y mostrar resumen del archivo en memoria (máx. 1 MB, solo PDF). Mensajes de límite y tipo de archivo. Acción para reemplazar archivo. Continuar → register_skills.
- El archivo se mantiene en el dispositivo hasta register_consent.



Pantalla "Skills":
- Ruta: register_skills.
- Rubro profesional: GET /api/v1/catalogs/sectors.
- Skills del rubro: GET /api/v1/catalogs/sectors/{sector_id}/skills; selección entre 3 y 12 skills.
- Avanza a register_preferences.



Pantalla "Últimas preferencias":
- Ruta: register_preferences.
- Sueldo esperado (mínimo y máximo), modalidades preferidas (Remoto, Presencial, Híbrido) y cargas horarias (Full time, Part time, Otro).
- Avanza a register_consent.
- Para matching oficial cuentan: contenido del CV (con fairness), modalidades, cargas horarias y años de experiencia (dimensión experience_score). No influyen en el score: skills de perfil, presentación personal del perfil, rango de sueldo esperado, sueldo ofrecido de la oferta ni nacionalidad.



Pantalla "Uso de datos":
- Ruta: register_consent.
- Texto informativo y casilla "He leído y acepto el uso de mis datos personales conforme a la Política de Privacidad".
- Al aceptar → POST /api/v1/auth/register/candidate (multipart: parte data JSON con consent_given=true y parte file PDF).
- Éxito: JWT CANDIDATE → session.
- Antes de esta pantalla no hay Bearer de candidato; solo GET de catálogos y estado local en la app. Si el usuario cierra la app antes de aceptar, debe reingresar datos.



Pantalla "Ofertas" (feed principal):
- Ruta: session (HomeScreen).
- Carga: GET /api/v1/candidate/jobs/feed?page=1&size=20.
- Por oferta: imagen (GET /api/v1/candidate/jobs/{job_id}/image con Bearer si aplica), título, empresa, sueldo, comuna, modalidad, años de experiencia requeridos, descripción truncada, preview de skills (hasta 4), porcentaje y barra de matching (cinco dimensiones según Contrato).
- Swipe izquierda → POST /api/v1/candidate/swipes con action PASS.
- Swipe derecha → diálogo "¿Seguro de postular?" → POST /api/v1/candidate/applications.
- Botón guardar oferta → POST /api/v1/candidate/saved-jobs (idempotente).
- "Ver detalles" → job_detail/{job_id}.
- Tras postular puede abrirse application_preview/{application_id}.
- Barra inferior (CandidateMainBottomBar): Perfil, Ofertas (activo), Guardadas, Postulaciones.
- Menú de sesión (engranaje): cerrar sesión (limpia token y caché de guardadas).
- Pendiente: acceso a bandeja Matchs desde cabecera o navegacion (GET /api/v1/messaging/conversations).



Pantalla "Oferta Detalles":
- Ruta: job_detail/{job_id}.
- GET /api/v1/candidate/jobs/{job_id}: descripción completa, hasta 8 skills, workload, match.score, match.explanation y match_breakdown.
- Toggle guardar/quitar guardada (GET/POST/DELETE saved-jobs).
- No incluye postular desde detalle; la postulación se hace desde el feed (session).



Pantalla "Guardadas":
- Ruta: saved.
- GET /api/v1/candidate/saved-jobs; misma estructura de item que el feed.
- Por fila: ver detalle → job_detail/{job_id}; quitar de guardadas → DELETE /api/v1/candidate/saved-jobs/{job_id}.



Pantalla "Mis Postulaciones":
- Ruta: applications.
- GET /api/v1/candidate/applications?page=1&size=50; ordenadas por match_score descendente en cliente.
- Estados visibles: APPLIED y VIEWED (CANCELLED no se listan tras cancelar).
- Por fila: nombre oferta, empresa, sueldo, estado. Al pulsar → application_preview/{application_id}.



Pantalla "Vista Previa Oferta" (postulación):
- Ruta: application_preview/{application_id}.
- GET /api/v1/candidate/applications/{application_id}: datos de la oferta, estado APPLIED o VIEWED.
- Botón "Eliminar Postulación" → DELETE /api/v1/candidate/applications/{application_id} (modal confirmación; status CANCELLED).
- "Ir a Oferta" → job_detail/{job_id}.



Pantalla "Perfil":
- Ruta: profile.
- GET /api/v1/candidate/profile; edición por secciones con PATCH /api/v1/candidate/profile.
- CV: POST /api/v1/candidate/cv, GET /api/v1/candidate/cv/current, GET /api/v1/candidate/cv/current/file (visualizar/descargar en overlay).
- Catálogos para edición: mismos GET /api/v1/catalogs/* que en registro.
- Barra inferior igual que en Ofertas.



Pantalla "Aviso de match" (pendiente):
- Modal a pantalla completa tras login exitoso cuando GET /api/v1/messaging/conversations/login-notice devuelve item.
- Texto: "¡Una empresa quiere hacer match contigo!" con nombre comercial de la empresa (no nombre del reclutador).
- Boton principal "Ver mensajes" → abre el hilo de esa conversacion y PATCH dismiss-login-notice.
- Boton cerrar (X) o equivalente → PATCH dismiss-login-notice sin abrir hilo; continua flujo normal (session/Ofertas).
- Regla: si el candidato ya vio o cerro este aviso una vez para esa conversacion, no vuelve a mostrarse en logins posteriores.
- La mensajeria ya esta abierta para ambos desde que el reclutador establecio match con primer mensaje; el candidato no acepta ni rechaza el match.



Pantalla "Matchs" (bandeja de entrada; pendiente):
- Acceso desde navegacion principal (p. ej. pestana o entrada en barra inferior; a definir en UI).
- GET /api/v1/messaging/conversations: listado de conversaciones activas ordenadas por ultimo mensaje.
- Por fila: nombre comercial empresa, titulo oferta, preview ultimo mensaje.
- Al pulsar fila → Hilo de mensajes con empresa.



Pantalla "Hilo de mensajes con empresa" (pendiente):
- Historial y envio de mensajes; polling GET /api/v1/messaging/conversations/{id}/messages; POST mensajes.
- Cabecera: solo nombre comercial de la empresa.
- Mensajeria asincrona clasica: leer mensajes enviados por reclutador desde frontWeb y escribir/enviar respuestas.
- "Volver" → Matchs.
